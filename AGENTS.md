# Loggair Mandates

- **Rank-Zero Console:** In distributed environments, console output MUST be filtered to Rank 0 only. File logging captures all ranks with rank tags.
- **Multiprocess Safety:** All sinks MUST use Loguru's `enqueue=True` whenever multiple processes will write. The underlying `multiprocessing.SimpleQueue` is created **lazily** — deferred until something actually forks or spawns a child — so a request for `enqueue=True` does not allocate a POSIX semaphore in single-process runs. Hooks fire in `os.register_at_fork(before=...)` and a one-shot `multiprocessing.process.BaseProcess.__init__` patch. Set `LOGGAIR_EAGER_ENQUEUE=true` to force allocation at handler-creation time (rare; needed only when something bypasses both hook surfaces).
- **Log File Locations:** By default, Loggair resolves logs to `./logs`. However, in this workspace, the global configuration at `~/.config/loggair/config.yaml` redirects all logs to `~/logs` for centralized persistence. Always check `~/logs` when debugging local execution.
- **Startup Rotation:** Log files MUST be archived with timestamps on script start. Only the main rank/process performs rotation to prevent race conditions.
- **Runtime Rotation Is loguru's `rotation=`, ONE Rotator Per FILE:** The `rotation` knob (arg > `LOGGAIR_ROTATION` > YAML `rotation:` > `None`) passes loguru's `rotation=` verbatim to the FILE sink — never reimplement size/time parsing (loguru validates at `add()`, failing fast on bad values). On the SHARED file it MUST be applied only when `is_main_proc` (MainProcess AND rank 0); with `worker_files=True` each process exclusively owns its file and rotates its own. Rationale: rotation renames the active file, and a rename racing multiple writers splits streams — a spawn-started child that re-adds its own sink keeps its fd and writes into the rotated archive afterwards (documented caveat; fork-inherited children route through the enqueue queue and are safe). When rotation is active, `retention=` (same count) and `compression=` (same value) MUST also be passed at sink level so pruning/compression happen at rotation time — a service that never restarts otherwise never prunes. Empirically verified: loguru's retention is per-stem and live-log-safe, and it recognises Loggair's own startup archives of the same stem. Runtime archives carry a `_ffffff` microseconds suffix — `_TIMESTAMP_RE` keeps BOTH naming schemes recognised by the startup purges.
- **Framework Interception:** Standard Python `logging`, TensorFlow, PyTorch, and JAX logs MUST be automatically intercepted and routed through Loggair. The `InterceptHandler` frame walk MUST use the walk-up-from-frame-0 recipe (loguru's current recommendation), NEVER a hardcoded `sys._getframe(N)` — a hardcoded depth raises `ValueError` on shallow stacks (e.g. `emit()` called directly) and silently mis-attributes callers when the stdlib call path changes.
- **Interception Modes (`intercept` = closed `Literal["full","coexist","off"]`):** How invasive the stdlib takeover is, is a CONFIG KNOB, not a constant. `full` (default) = `basicConfig(force=True)` + strip named loggers to propagate; `coexist` = APPEND-only next to a framework that owns logging (uvicorn/gunicorn) — other root handlers and all named loggers untouched, root level lowered to DEBUG (the one shared knob coexistence needs; documented trade-off); `off` = no interception, no warnings redirect, no third-party defaults. `intercept_exclude` prefixes are hands-off ENTIRELY (handlers, propagate, level — dotted-children included; third-party defaults skip them too). `capture_warnings=False` leaves/restores `warnings.showwarning`. Validation set derives from `get_args(InterceptMode)` (one source of truth); invalid values fail fast. Never hard-code new interception behavior that ignores these knobs.
- **Per-Worker Files (`worker_files=True`) — Exclusive Ownership Unlocks Rotation:** When enabled, every non-main writer gets its OWN file (`{name}.rank{N}.log` for ranks, `{name}.{procname}.log` for children, both suffixes combined for a rank's children) instead of appending to the shared `{name}.log`. Consequences that MUST be preserved: (1) exclusive ownership makes rotation race-free, so per-worker files get startup rotation (`_rotate(..., force_owner=True)` — the rank gate protects only the SHARED file) AND runtime `rotation`; (2) the startup sweep still never deletes bare per-worker `.log` files (live-log-safe rule) — only their timestamped archives, per stem; (3) merge-at-read is the model (`lnav ./logs`), do NOT build a merged-write path. Default stays False (shared file, rank-tagged).
- **Third-Party Silence Defaults Must Yield to `module_levels`:** The chatty-logger defaults (`asyncio`/`httpx`/`urllib3`/`datasets`/`filelock` → stdlib `WARNING`, in `intercept._DEFAULT_THIRD_PARTY_LEVELS`) are applied at the STDLIB layer for zero per-record cost, but a user `module_levels` rule whose prefix targets one of those loggers MUST lift the stdlib gate to `NOTSET` (records then flow through interception to the per-sink Loggair filters). Never hard-silence a logger the user explicitly tuned — `configure_logging` passes the rule prefixes to `setup_interception(module_level_prefixes=...)` for exactly this reason.
- **TTY-Aware Console Color (NO_COLOR is the only env knob):** The console sink's `colorize` is a **tri-state** resolved by `_resolve_colorize(arg)`: explicit `configure_logging(colorize=...)` arg (`True`/`False`) → the standard `NO_COLOR` env (any non-empty → off, per no-color.org; empty `NO_COLOR=` re-allows) → `None` (default). `None` is loguru's auto-detect (`_colorama.should_colorize()` → `stream.isatty()` plus Jupyter/CI/PyCharm heuristics): colors on a real TTY, plain text when stderr is redirected or piped (`2> run.log` / `| tee`), so log files never accumulate escape codes. `NO_COLOR` is the ONLY environment control — do NOT add a bespoke `LOGGAIR_COLORIZE` (or any other) color env var, and there is no YAML `colorize:` config knob; the `colorize=` argument is the sole programmatic override. The console sink MUST pass the RESOLVED `colorize_val`, NEVER a hardcoded `True`/`None`. To change coloring after configuration (incl. the lazy auto-config the first `get_logger()` triggers), call `reconfigure(colorize=...)` (the `force=True` reload wrapper) — a plain second `configure_logging` without `force` is a no-op. **Non-interactive consumers (navigaitor, FluxStudio) MUST call `loggair.force_no_color()` at import — NOT a bare `os.environ.setdefault`.** Setting/inheriting the env var alone is NOT enough: once the console sink exists its `colorize` is baked, so if some earlier import already configured Loggair the late env change is ignored. `force_no_color()` does both — `setdefault("NO_COLOR","1")` (so child processes inherit it; a pre-set empty `NO_COLOR=` re-allows colors) AND `reconfigure()` when already configured (so the live sink reloads colorless now). Empirically pinned by the `force_no_color`/integration colorize tests.
- **Zero-Blocking:** Logging MUST never block the training critical path. Background sinking is mandatory.
- **Runtime Signals Defer to a Worker Thread — NEVER Touch loguru in a Signal Handler:** The `reload_signal` / `debug_signal` handlers (installed by `_install_signal_handlers`, main process + main thread only) MUST only spawn a worker thread (`_apply_signal_action`) and return. Empirically established: loguru's handler and core locks are plain non-reentrant `threading.Lock`s, and a Python signal handler runs in the MAIN thread at an arbitrary bytecode boundary — so a `logger.remove()`/`add()` from a handler that interrupted an in-flight `emit` (same thread already holds the lock) self-deadlocks. A worker thread instead waits for the lock like any other thread. The spawned thread is stored on `LoggingState.last_signal_thread` so tests join it deterministically (no sleeps). Config-file POLLING was considered and REJECTED (2026-07-04): a watcher thread in every process violates the zero-overhead principle, and `reload_signal` covers the edit-config-then-apply workflow without one.
- **`reconfigure` Re-applies the Last Explicit Args (`LoggingState.last_kwargs`):** `configure_logging` records its explicitly-passed (non-None) kwargs; `reconfigure(**overrides)` and the signal-triggered reload merge them UNDER the overrides. This fixed a real bug: `reconfigure(colorize=False)` (e.g. via `force_no_color()`) after `configure_logging(log_dir="./x")` used to re-resolve `log_dir` from config files/defaults and silently PIVOT the live log to another directory. Consequence of the precedence hierarchy: an arg-pinned setting is NOT signal-reloadable — drive settings via env/config files when they must be changeable at runtime (documented in README §12). The debug toggle snapshots `last_kwargs` before elevating and restores the snapshot on toggle-off.
- **Experiment Context (`loggair.context` module) — Process-Global, Copy-on-Write, setdefault Into Records:** `set_context`/`clear_context`/`get_context`/`context` maintain ONE process-wide dict (deliberately NOT contextvars — a checkpoint-saver thread's records must carry the epoch the training thread set; loguru's `contextualize` is invisible to sibling threads). Writers hold the module lock and PUBLISH a brand-new `(dict, prebuilt tag)` pair atomically; the per-record sink-filter read (`context_snapshot()`) is lock-free and must stay that way — never mutate the published dict in place, and never add per-record locking or tag formatting (the tag is prebuilt at WRITE time). The filter stamps `extra["context_tag"]` unconditionally (empty string default — the `rank_tag` pattern, so `{extra[context_tag]}` in the DEFAULT formats never KeyErrors) and copies the individual fields into `extra` via `setdefault` — an explicit `logger.bind(epoch=...)` always wins over ambient context. `reset_logging()` clears the context; `get_active_config()` reports it live.
- **Alerting Is Apprise-Backed, Enqueue-Only in the Logging Path — and `logprise` Is REJECTED:** The `alert_urls`/`alert_level`/`alert_throttle` knobs route high-severity records through `loggair.alerts.AlertDispatcher`: the loguru sink ONLY enqueues (zero-blocking mandate); one daemon worker batches everything since the last delivery into a single apprise notification, holding deliveries to one per `alert_throttle` window (storm collapse). Invariants: (1) apprise is an OPTIONAL `[alerts]` extra, lazy-imported with a `pip install loggair[alerts]` error — never a hard dep, never per-platform HTTP code in loggair; (2) invalid URLs fail fast via `Apprise.add()` returning False (verified offline behavior) — no silent dropped destinations; (3) delivery failures are logged via a `loggair_alert_internal`-bound WARNING that the alert sink's filter DROPS — a failing webhook must never alert about itself (loop guard, test-pinned); (4) `get_active_config` exposes ONLY apprise privacy-redacted URLs (`url(privacy=True)`) — raw alert URLs carry tokens and MUST NOT appear in any diagnostics payload; (5) `flush()` clears `_wake` after draining and the worker HOLDS before delivering — do not "simplify" this back to wait-after-deliver, it reintroduces the racy premature deliveries the batching test caught. **`logprise` evaluated 2026-07-04 and rejected** (do not re-propose): import-time process-global side effects (own stdlib interception via `basicConfig(force=True)` + `logging.Logger._log` patch that fights Loggair's, a `loguru._Logger.remove` patch incompatible with reconfigure/reset, sys.excepthook/atexit hooks) and an hourly-digest delivery model, vs. this feature's immediate alerting.
- **`resolve_settings()` Is the ONE Resolver and It MUST Stay Pure — and `python -m loggair` MUST Stay Read-Only:** Configuration resolution (the full hierarchy incl. validation, script-name/worker-suffix derivation) lives ONLY in `core.resolve_settings()`; `configure_logging` consumes its output and performs the side effects (mkdir, rotation, sinks, interception, signals, env writes) AFTERWARDS — never re-inline resolution or add a side effect to the resolver (the `python -m loggair` diagnostic calls it next to LIVE runs; a resolver that mkdirs or a diagnostic that rotates is a footgun, pinned by `test_main_reports_without_configuring_or_rotating` and `test_resolve_settings_is_side_effect_free`). The resolver returns public JSON keys (the `get_active_config` vocabulary — the snapshot is DERIVED from it, keep it that way) plus `_`-prefixed internals; `_alert_urls` is RAW and must never be printed — the diagnostic masks everything after the scheme (`slack://****`), deliberately NOT apprise's per-field redaction (optional dep). The diagnostic reports resolution `ValueError`s with context and exit 1 instead of crashing — broken config is its primary use case. Rank detection is shared via `discovery.detect_rank()` (uncached, returns `(rank, source)`); the cached `get_rank()` wraps it — never duplicate the env-var priority list. The diagnostic ships BOTH as `python -m loggair` AND as the `loggair` console script (`[project.scripts]`): entry-point scripts have no cwd on sys.path, so the script works from a workspace root whose `loggair/` project folder namespace-shadows the editable install; the `-m` form MUST keep the shadow guard at the top of `__main__.py`: it detects `__file__ is None` (under an editable install the meta-path finder supplies `__main__` while the package resolves to the empty cwd namespace — empirically established 2026-07-06; wheel installs are immune because a regular package beats a namespace portion in the path scan) and SELF-HEALS — removes the sys.path entry that contributed the shadow, forgets the bad module, re-imports the real package, and runs the FULL report with the hazard surfaced (`WARNING:` line / `shadowed_path_ignored` JSON field — plain `import loggair` scripts from that cwd still break, the user must know). This path REMOVAL is a scoped exception to the no-sys-path-hacks mandate: inverse direction (the mandate bans ADDING cwd), diagnostic-process-only, post-detection, reported — never replicate it in library code. Exit 2 remains only for the unhealable case (no real installation reachable).
- **`get_active_config()` Must Track Every Knob (JSON-Serializable, Read-Only):** `configure_logging` snapshots its RESOLVED settings into `LoggingState.active_config`; the public `get_active_config()` serves a fresh copy. Invariants: (1) **every new `configure_logging` knob MUST be added to the snapshot in the same change** — a knob missing from introspection is silent drift; (2) the dict stays **JSON-serializable** (paths as `str`, `module_levels` as the validated raw mapping — this is the future navigaitor MCP tool payload); (3) the call is **read-only** — it must NEVER trigger the lazy configuration (returns `{"configured": False}` when unconfigured); (4) live flags that change without a re-snapshot (`enqueue_active`, `debug_mode_active`) are read from `LoggingState` at call time, not baked into the stored snapshot.
- **Sink Formats Are Config Knobs, Never Inline Literals:** The per-sink loguru format strings live in the PUBLIC module constants `DEFAULT_CONSOLE_FORMAT` / `DEFAULT_FILE_FORMAT` (exported so users extend instead of restating) and are overridable via `console_format` / `file_format` through the full hierarchy (arg > `LOGGAIR_CONSOLE_FORMAT`/`LOGGAIR_FILE_FORMAT` > YAML/pyproject > defaults). Never re-hardcode a format inline in `configure_logging`. BOTH sink filters stamp `record["extra"]["rank_tag"]` UNCONDITIONALLY (the stamp lives in `_make_sink_filter`, not the format), so `{extra[rank_tag]}` is available to any custom format and a format omitting it must not break rank tagging elsewhere. Validation reality (empirically established): invalid color MARKUP fails fast at `add()`; a nonexistent FIELD does not — loguru emits a loud per-record error report on stderr and drops the record. Document that trade-off wherever formats are surfaced; do not try to pre-render formats against synthetic records to force fail-fast (private-API territory).
- **Configuration Hierarchy:** Resolution order: function args > env vars (`LOGGAIR_`) > local YAML > local pyproject.toml > XDG global config > defaults. Never violate this precedence. Resolution MUST be **presence-based** (`is not None` / `key in cfg`), NEVER truthiness-`or`-chained — an `or`-chain silently swallows falsy-but-valid values (`rotation_on_startup: false`, `retention: 0`), which is exactly the bug fixed in `configure_logging.resolve`. An empty-string env var counts as unset. Config files merge SHALLOWLY (a local `module_levels:` replaces the global one wholesale); this is documented behavior, not a bug.
- **`get_logger(name)` Overrides `record["name"]`:** A name passed to `get_logger` MUST take effect — it is applied via `logger.patch` (a module-level `_set_record_name` through `functools.partial`, NOT a lambda) so it shows as the `{name}` field on both sinks and participates in `module_levels` prefix matching, mirroring `logging.getLogger(name)` semantics. Never regress this to `logger.bind(name=...)`: `bind` writes to `record["extra"]`, which neither the sink formats nor the filters read — that was the silent no-op bug.
- **Retention Is Per-Stem and Archives-Only (Live Logs Are Sacred):** BOTH retention purges — `_rotate`'s and the startup sweep in `configure_logging` — keep `retention` *timestamped archives* per stem (`_ARCHIVE_RE`, compressed or plain). The sweep also prunes stems left behind by earlier runs under other script names, but a bare `{name}.log` of another script MUST NEVER be a purge candidate: in a shared log dir (the workspace's centralized `~/logs`) it may be the ACTIVE sink of a concurrently running process, and unlinking it silently discards that run's output (loguru keeps writing to the unlinked inode). Pinned by `test_sweep_never_deletes_other_scripts_live_logs`. Corollary: purges MUST tolerate archives VANISHING mid-purge — in that same shared dir another process may purge the same stem concurrently, so any candidate can disappear between the directory listing and the `stat()`/`unlink()` in `_purge_old_files` (a TOCTOU race no pre-check can close — the sanctioned try/except exception to the check-first mandate). A vanished candidate is someone else's completed purge: skip it silently, never warn, still enforce `retention` on the survivors. Pinned by the two `test_purge_tolerates_*` tests.
- **Per-logger Levels (`module_levels`):** Per-sink, per-logger overrides live at the same precedence layer as `file_level` / `console_level` — no new layer. Schema is a nested dict keyed by dotted logger-name prefix; per-rule fields (`console`, `file`, `workers_only`) MUST fail-fast on unknown keys or invalid level strings. Silent ignores are how this feature rotted unimplemented for months — never reintroduce them.
- **Runtime Kill-Switch (`NullLogger` + `LOGGAIR_DISABLE_*`):** `get_logger()` returns a no-op `loggair.null_logger.NullLogger` when `LOGGAIR_DISABLE_LOGGING` is truthy (every process) or `LOGGAIR_DISABLE_MULTIPROCESS_LOGGING` is truthy AND `current_process().name != "MainProcess"` (worker/child processes only). The gate (`_logging_disabled()`) sits at the TOP of `get_logger`, BEFORE the lazy `configure_logging()` — so the common path creates NO file/sink/queue when disabled (that is the whole point: zero overhead for perf runs / test suites). The disable flags gate `get_logger` ONLY; an explicit `configure_logging()` still builds sinks. `NullLogger` MUST stay API-compatible with the slice of loguru that call-sites touch: log methods are no-ops, `bind`/`opt`/`patch` return a logger (chains keep flowing), `level(name).no` returns the numeric level, `contextualize`/`catch` return working context-manager / decorator stand-ins, and `__getattr__` returns a no-op callable for everything else (so an unforeseen loguru call can't raise just because logging is off) — but it MUST re-raise `AttributeError` for dunders so the object stays picklable (spawn-safe). `get_logger` returns it via `cast("Logger", ...)` to keep the public return type for consumers.
- **Compression: Loggair's `_rotate` for STARTUP archives, loguru's sink for RUNTIME archives (`compression="gz"|"zip"`):** Loggair does its OWN startup rotation (it RENAMES `{name}.log` → `{name}.{ts}.log` in `_rotate`, with loguru-managed rotation disabled by default). On that path loguru's sink-level `compression=` never fires and MUST NOT be relied upon — it would be a silent dead knob. The ONE exception: when the runtime `rotation` knob is active, the SAME `compression` value IS passed at sink level (see the Runtime Rotation mandate) because loguru-managed rotation then genuinely fires; both mechanisms take the identical `"gz"`/`"zip"` vocabulary, one config knob. Compression is applied by `_compress_file` immediately after the rename inside `_rotate`, and is **best-effort**: any failure warns, cleans up the partial archive, and returns the ORIGINAL uncompressed path so a rotated log is never lost and logging never breaks. The accepted formats are a closed `Literal["gz", "zip"]` (`CompressionFormat`) — the runtime validation set is `get_args(...)` of it (one source of truth, per the closed-`Literal` mandate), and an invalid value raises `ValueError` at configure time. BOTH retention purges (the per-stem one in `_rotate` and the per-stem archive sweep in `configure_logging`) MUST recognise compressed archives (the `_COMPRESSION_RE` optional-suffix regex, folded into `_ARCHIVE_RE`) or compressed archives would accumulate unbounded. Resolution follows the standard hierarchy: arg > `LOGGAIR_COMPRESSION` > YAML `compression:` > `None`.
- **Structured JSON Output Is loguru's `serialize=True`, Never a Hand-Rolled Formatter:** The `serialize` knob (arg > `LOGGAIR_SERIALIZE` > YAML `serialize:` > `False`) passes loguru's native `serialize=True` to BOTH sinks — one `{"text": ..., "record": {...}}` JSON object per line. Do NOT reimplement JSON rendering with a custom `format=` string: loguru's serializer carries the full structured record (level, timestamp, name/function/line, process/thread, `extra` incl. `rank_tag`) and stays in lock-step with loguru upgrades. `serialize=True` MUST force the console `colorize` to `False` (overriding the arg and `NO_COLOR`-derived tri-state): ANSI escapes would otherwise be embedded inside the JSON `text` field (verified empirically — loguru colorizes BEFORE serializing). Rank filtering, `module_levels`, rotation/retention, and lazy-enqueue compose unchanged (serialize rides inside `file_sink_params`, so the enqueue upgrade keeps it).
- **Config Loader Stays Bespoke — Do NOT Adopt `loguru-config`:** Evaluated 2026-07-04 and rejected. `loguru-config` (PyPI, single 0.1.0 release from 2023-07, ~545 LOC) maps a config file DIRECTLY onto `logger.configure()` handler specs — the user declares raw sinks. That is the wrong abstraction for Loggair, whose config keys (`log_dir`, `script_name`, `rotation_on_startup`, `retention`, `compression`, `module_levels`, `enqueue`, `serialize`) are POLICIES that Loggair compiles into sinks + filters + rotation/pivot/lazy-enqueue behavior; raw handler specs would bypass rank-zero filtering, rank tags, `module_levels`, startup rotation, and the colorize tri-state entirely. It also has no resolution hierarchy (one file; no env vars, no `pyproject.toml` table, no XDG fallback) and is effectively unmaintained. `loggair/config.py` (~50 LOC) already covers everything Loggair needs — keep it.
- **Packaging — distribution `loggair` == import `loggair`:** Distribution and import package share the name `loggair` — verified free on PyPI (2026-07-05) and distinct under Warehouse's ultranormalization similarity check (`logair`, one g, is a different registered project; the extra letter is not a separator/case variation, so the check passes). Naming history (do NOT relitigate): this project was previously `loggair` (import) / `log-flow` → `loggair-ml` (dist); the bare `loggair` PyPI name is squatted by an abandoned alpha and `log-flow` was rejected by the similarity check, which motivated the clean `loggair` identity where dist == import. Packaging invariants the build depends on: `pyproject.toml` `[tool.setuptools.package-data] loggair = ["py.typed"]` ships the PEP 561 marker, and `MANIFEST.in` ships `loggair.example.yaml` + `CHANGELOG.md` in the sdist (top-level non-package files are NOT auto-included). **Metadata is PEP 639**: `license = "MIT"` is a plain SPDX string (build-system floor `setuptools>=77`) and the `License :: OSI Approved :: MIT License` classifier is deliberately ABSENT — re-adding either the TOML-table license or the classifier reintroduces `SetuptoolsDeprecationWarning`s at build time. **`__version__` has ONE source of truth**: `pyproject.toml` `version`, read at runtime via `importlib.metadata.version("loggair")` in `loggair/__init__.py` (source-checkout fallback `0.0.0.dev0`) — never hardcode a second version string anywhere; after bumping, re-run `pip install -e` so editable metadata catches up. Validate any packaging change with `python -m build` (expect ZERO deprecation warnings) + `twine check --strict dist/*` (both in the `dev` extra) before considering it done. **Releases are tag-driven**: bump `version`, retitle the CHANGELOG `[Unreleased]` section, then `git tag v<version> && git push origin v<version>` — the hand-written `.github/workflows/release.yml` (NOT aisland-generated; regeneration must never touch it) guards tag==pyproject version, builds, twine-checks, smoke-tests the wheel in a clean venv, and publishes via PyPI Trusted Publishing (OIDC, `environment: pypi`, no stored token; one-time pending-publisher setup on pypi.org documented in the workflow header). The README install section is pip-first (`pip install loggair`) with the GitHub URL as the development alternative.

## Testing & Validation
- **No Sleep Loops:** NEVER use `time.sleep()` for synchronization. Use `logger.complete()`, `join()`, or `close()`.
- **Environment Isolation:** Tests MUST mock HOME and XDG_CONFIG_HOME. The autouse conftest fixture calls the public `reset_logging()` between tests — the full teardown that also restores `warnings.showwarning`, the stdlib root handler, and the `BaseProcess.__init__` patch (not just `LoggingState.reset()`).
- **Line Length:** 120 characters (Black, isort, flake8).
